Strong information design on an unfinished design system

The dashboard frontend (React 18, Vite, Tailwind, shadcn-style primitives, React Query) is a thoughtfully structured operator console with genuinely good information design and accessibility instincts in places. It is held back by an incomplete theming migration, two concrete button defects, and uneven accessibility. None are architectural blockers and most are short, high-leverage fixes.

Outcome

Plain-English verdict

Good bones

This is a capable, well-organized operator console. Layout is responsive and considered (a real mobile card layout for the activity list, desktop tables, safe-area insets, a sheet drawer for mobile nav). Loading, empty, and error states exist almost everywhere. The status and failure-type badges encode meaning with color plus icon plus text, which is colorblind-safe.

The dominant theme across the issues is a half-finished design-system migration. The team built a clean semantic token set (the --ph-* CSS variables) and themed some components to it (Badge, Card, the status badges), but the form primitives (Input, Select, Switch, Tabs) still carry the stock shadcn slate/azure palette, and raw Tailwind colors (azure-*, gray-*, rose-*, red-*, emerald-*) are scattered through the pages. The result is inconsistent surfaces and focus states, plus one primary-button defect that ships with no hover feedback.

The accessibility story is the same shape: SettingToggleField is genuinely exemplary (label association, aria-describedby, aria-live, screen-reader-only text), which proves the team knows how to do this. The verification form and the dashboard charts then do not follow that pattern. The capability is there; it is applied unevenly.

Recommended next action

One focused pass

Do a single "design-system consolidation" PR before any new feature work:

1. Fix the two button defects (no hover, no focus ring) in one file. 2. Re-theme the four form primitives (Input, Select, Switch, Tabs) from gray-*/azure-* onto --ph-* tokens. 3. Replace the remaining raw color literals with tokens.

That is roughly a day of work, touches mostly leaf files, and removes the bulk of the visible polish gaps and the worst keyboard-accessibility issues at once.

Theme drift

The design-system split, in detail

There are effectively two visual languages in the codebase. Consolidating onto the --ph-* tokens is the single highest-leverage change because it resolves several findings at once (surface mismatch, focus-ring color, the five reds, and the StatsCard contrast risk).

Themed correctly

Badge, Card, StatusBadge, FailureTypeBadge, Layout, and the marketing Landing page all use --ph-* tokens consistently. This is the target state.

Stock shadcn, not themed

Input, Select, Switch, and Tabs still ship the generated defaults: bg-gray-100/dark:bg-gray-700, text-gray-900, and focus:ring-azure-500. They visibly differ from the cards they sit inside.

Three focus treatments

Form primitives ring azure-500 (blue), the verification <textarea> rings --ph-accent (amber), and Button rings nothing. Pick one (the accent) and apply it everywhere.

The button defect, exactly

The default variant string is:

default: 'bg-[var(--ph-accent)] text-white hover:opacity-92'

Tailwind's default opacity scale is 0, 5, 10, 20, 25, 30, 40, 50, 60, 70, 75, 80, 90, 95, 100. There is no 92, and tailwind.config.js does not extend opacity, so hover:opacity-92 compiles to nothing and the primary button has no hover state. Use hover:bg-[var(--ph-accent-hover)] (the token already exists in index.css) or hover:opacity-[0.92] with arbitrary-value syntax.

Honesty

What was not verified

This is a static, code-level review. The app was not run in a browser, so visual rendering, real focus behavior, and live interactions were not observed. No automated accessibility scan (axe / Lighthouse) and no contrast measurement were run; contrast notes are by inspection of token values against surfaces.

The two largest files, AdminControlsForm.tsx (3350 lines) and ActivityDetail.tsx (2681 lines), were sampled rather than read end to end. Findings there are representative of patterns seen, not an exhaustive enumeration. Their size is itself worth noting: components this large are hard to test and maintain, and are good decomposition candidates.
