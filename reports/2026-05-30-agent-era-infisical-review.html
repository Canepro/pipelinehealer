Agent-era evolution and Infisical migration review

PipelineHealer already has the right shape for an agent operations product: evidence normalization, policy gates, operator settings, learning feedback, and deployment adapters. The next phase should turn those into a durable agent control plane rather than add a loose chat layer.

Verdict

Recommended direction
Keep the product identity

The strongest positioning is policy-aware pipeline remediation. In the agent era, the product should become the governed runtime where delivery agents operate with evidence, approvals, provenance, and rollback.

Promote agents into durable workers

The current background task model works for a demo and small deployment, but agentic execution needs a resumable work queue, idempotency, leases, retries, and replayable traces.

Use Infisical as source of truth

Infisical should own project, runtime, CI/CD, and service secrets. Existing adapters can keep injecting env vars, ACA secret refs, Helm secrets, or runtime write-only secrets during staged cutover.

How The App Should Evolve

Product fit is strong

1. Agent Control Plane

Make PipelineHealer the place where delivery agents receive work, request tools, prove outcomes, and surface uncertainty. Keep policy, provenance, and operator verification as first-class objects.

  • Durable work queue with activity leases and retry policy.
  • Tool invocation ledger: requested, allowed, denied, executed, output hash, human approval.
  • Replayable incident timelines for every automated decision.

2. Provider and Tool Router

Replace the global provider boundary with a router that maps tasks to models and tools by cost, capability, repo risk, and confidence.

  • Analysis can use cheaper models; diagnosis and patch drafting can use stronger coding models.
  • External diagnostics can choose GitHub MCP, GH-AW, Jenkins, Azure Monitor, or custom integrations by policy.
  • Every route should expose why it was chosen.

3. Real Learning Memory

The learning system should become a governed remediation memory: evidence summaries, applicability rules, risk notes, retrieval traces, and retirement criteria.

  • Use LLMs to draft candidate playbooks from verified incidents.
  • Inject active playbooks as structured context, not prompt stuffing.
  • Track helped, hurt, stale, overridden, and retired outcomes.

4. Agent Handoff Network

The existing Assign-to-Agent path is a good starting point. Turn it into a typed handoff protocol for external agents and humans.

  • Handoff destinations should advertise capabilities and health.
  • Use signed requests, allowlists, idempotency keys, and bounded payloads.
  • Accept responses back into the same activity timeline.

Execution sequence

  1. Create an Infisical project or confirm the existing project, environments, and folders. Record only project slug/id, environment, folder path, and secret names.
  2. Add a repo doc such as docs/runbooks/INFISICAL_SECRETS.md with secret ownership, consumer, rotation, rollback, and proof rules. Do not include values.
  3. For local/dev, use infisical run --env dev --path /backend -- bash scripts/ph.sh ... or generate a short-lived local env file only for approved smoke tests.
  4. For Azure Container Apps, keep the existing --secure-secrets path but populate the process environment from Infisical during deploy, then let ACA secret refs remain the runtime injection boundary.
  5. For Kubernetes, add Helm support for existingSecret or External Secrets Operator with Infisical provider, then stop rendering production secrets through plain values files.
  6. For UI-managed runtime secrets, add a future infisical SETTINGS_SECRET_BACKEND adapter only after the external deploy paths are stable.
  7. Cut over one consumer class at a time: backend auth, LLM keys, GitHub, Jenkins, storage, handoff, CI. Verify each with redacted smoke proof before deleting old paths.

Approval gates

  • Value movement: requires explicit approval for the specific source, target, environment, and rows.
  • Rotation: requires owner sign-off and rollback path.
  • Production cutover: requires redacted proof that the consumer reads from the Infisical-backed path and the old path can be disabled safely.
